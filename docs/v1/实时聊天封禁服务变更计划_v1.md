## 1. 目标与范围

### 1.1 目标

1. 启动一个常驻 Node 服务，同时提供网页前端。
2. 玩家在前端输入框发送聊天消息。
3. 消息入库后触发 Agent 分析该玩家最近一段时间的消息。
4. Agent 输出风险判断与处罚建议：`1min`、`1h`、`1天`、`3天`、永久封禁。
5. 封禁生效后，该玩家不能继续发消息，直到封禁到期或被手动解除。
6. 前端提供封禁状态、倒计时、提前解封按钮。
7. 前端可切换玩家，便于测试不同账号。

### 1.2 本期不做

- 生产级登录鉴权、多租户、HTTPS。
- 分布式部署、消息队列、Redis。
- 复杂管理后台、统计报表。
- 自动封禁申诉流程。
- 真正的游戏客户端接入。

## 3. 消息处理流程

### 3.1 发送消息

```text
玩家点击发送
  → POST /api/players/:account/messages
  → 查询是否有 active 封禁
      ├─ 有：返回 423 Locked + 封禁信息，不入库
      └─ 无：
          1. 写入 chat_risk_logs（无任何标签）
          2. 返回 202 Accepted + messageId + analysisStatus=pending
          3. 后台按账号排队分析
```

### 3.2 Agent 分析

```text
分析任务
  → 读取该账号最近 N 分钟、最多 M 条消息
  → 追加最近 24h 风险/封禁摘要（只传统计，不传全部历史）
  → 调用 Agent
  → 解析严格 JSON
  → 写入 chat_risk_judgements
  → 若处罚不是 none：创建 chat_player_bans
  → SSE 推送 analysis_completed / ban_started
```

### 3.3 封禁校验

封禁生效后：

- 前端输入框禁用，显示剩余时间。
- 服务端再次校验，防止绕过前端直接调用 API。
- 到期后自动视为过期；下一次请求时更新状态。
- 手动解封：`POST /api/players/:account/unban`，把 active 封禁置为 lifted。

## 4. Agent 分析设计

### 4.1 时间跨度建议

**默认：最近 10 分钟，最多 50 条消息。**

理由：

- 聊天风险通常发生在连续对话中，10 分钟足以覆盖刷屏、连续引流、辱骂升级等场景。
- 50 条消息约 2k~5k tokens，单次分析延迟可控。
- 不把全天消息塞给模型，避免成本、延迟和上下文污染。
- 另查最近 24 小时的风险/封禁统计用于升级处罚，但不把原文全部传入。

推荐可配置：

```text
CHAT_ANALYSIS_WINDOW_MINUTES=10
CHAT_ANALYSIS_MAX_MESSAGES=50
CHAT_ANALYSIS_LOOKBACK_HOURS=24
```

如果后续发现 10 分钟不够，可调整到 30 分钟 / 100 条；不建议默认超过 30 分钟。

### 4.2 Agent 输入

```json
{
  "player": {
    "account": "account_01",
    "nickname": "清风",
    "area": "一区/server_11"
  },
  "window": {
    "minutes": 10,
    "messageCount": 37
  },
  "recentMessages": [
    {
      "id": "log_000123",
      "create_time": "2026-10-21 10:01:02.123",
      "content": "加我 VX 详聊",
      "context": []
    }
  ],
  "historySummary": {
    "last24hRiskCount": 3,
    "last24hBanCount": 1,
    "lastBan": {
      "reason": 5,
      "punishment": "ban_1h",
      "startedAt": "2026-10-21 08:30:00"
    }
  }
}
```

### 4.3 Agent 输出

必须为严格 JSON：

```json
{
  "is_risk": true,
  "reason": 5,
  "label": "广告诈骗",
  "confidence": 0.92,
  "punishment": "ban_1h",
  "duration_seconds": 3600,
  "evidence": ["加我 VX 详聊"],
  "summary": "该玩家在 10 分钟内多次发布站外联系方式，存在引流广告行为。"
}
```

处罚枚举：

| punishment | 时长 |
| --- | --- |
| `none` | 不封禁 |
| `ban_1m` | 60 秒 |
| `ban_1h` | 3600 秒 |
| `ban_1d` | 86400 秒 |
| `ban_3d` | 259200 秒 |
| `permanent` | 永久 |

### 4.4 处罚安全护栏（具体设计）

原则：**Agent 只给建议，服务端决定最终处罚**。服务端不因 Agent 一句话直接永久封禁，而是根据风险类型、置信度、最近 24h 封禁次数取上限。

#### 4.4.1 处罚等级

| punishment | 排位 | 时长 |
| --- | --- | --- |
| `none` | 0 | 不封禁 |
| `ban_1m` | 1 | 60 秒 |
| `ban_1h` | 2 | 3600 秒 |
| `ban_1d` | 3 | 86400 秒 |
| `ban_3d` | 4 | 259200 秒 |
| `permanent` | 5 | 永久 |

服务端只信任枚举，不信任 Agent 传入的 `duration_seconds`；秒数由枚举映射。

#### 4.4.2 风险类型分级

| 严重度 | reason | 说明 | 无前科时最高处罚 |
| --- | --- | --- | --- |
| `low` | `0` 其他违禁、`7` 特殊字符、未知 reason | 低危或信息不足 | `ban_1h` |
| `medium` | `3` 侮辱谩骂、`6` 运营规避 | 常见违规 | `ban_1d` |
| `high` | `1` 政治宗教、`2` 色情低俗、`127` 渠道禁止、`-128` 访问屏蔽 | 高危内容 | `ban_3d` |
| `critical` | `4` 暴恐犯罪、`5` 广告诈骗 | 严重风险 | `permanent`，但必须满足重复违规条件 |

#### 4.4.3 置信度上限

| Agent confidence | 最高处罚 |
| --- | --- |
| `< 0.60` | `none` |
| `[0.60, 0.80)` | `ban_1h` |
| `[0.80, 0.90)` | `ban_1d` |
| `[0.90, 0.95)` | `ban_3d` |
| `>= 0.95` | `permanent`，但仍受重复违规条件限制 |

#### 4.4.4 重复违规上限

统计该账号最近 24 小时内 `chat_player_bans` 的历史条数（包含已过期、已手动解除）：

| 最近 24h 历史封禁数 | `permanent` 是否允许 |
| --- | --- |
| `0` | 否，最高 `ban_3d` |
| `1` | 仅 `critical` 且 `confidence >= 0.95` 时允许 |
| `>= 2` | `high` / `critical` 且 `confidence >= 0.95` 时允许 |

`permanent` 不允许时，最高降级为 `ban_3d`。

#### 4.4.5 最终处罚算法

```text
requested = Agent 输出的 punishment
rank(x)   = none:0, 1m:1, 1h:2, 1d:3, 3d:4, permanent:5

if !is_risk or reason == -1:
    applied = none

else:
    severityCap   = 风险类型分级上限
    confidenceCap = 置信度上限
    repeatCap     = 重复违规上限
    appliedRank   = min(rank(requested), rank(severityCap), rank(confidenceCap), rank(repeatCap))
    applied       = rankToPunishment(appliedRank)
```

规则：

1. 服务端只降级，不升级；Agent 要求 `ban_1m` 时不会因历史记录自动变成 `1h`。
2. `is_risk=false` 或 `reason=-1`：不封禁。
3. `is_risk=true` 但 `reason=-1`，或 `is_risk=false` 但 `reason!=-1`：视为异常，不封禁，标记人工复核。
4. JSON 解析失败、字段缺失、动作非法、超时：不封禁，记录 `manual_review`。
5. 标签以服务端 `reason map` 为准；Agent 返回的 `label` 仅作参考，不一致时记录 policy note。
6. 最终动作映射：
   - `permanent` → `加入黑名单`
   - `ban_1m/1h/1d/3d` → `封禁`
   - `none` 且 `is_risk=true` → `人工复核` 或 `观察`
   - 正常 → `放行`

#### 4.4.6 示例

| Agent 建议 | reason | confidence | 24h 历史封禁 | 服务端结果 | 原因 |
| --- | --- | --- | --- | --- | --- |
| `permanent` | 5 广告诈骗 | 0.93 | 0 | `ban_3d` | 无前科，永久降级为 3 天 |
| `ban_1d` | 3 侮辱谩骂 | 0.72 | 0 | `ban_1h` | 置信度上限为 1 小时 |
| `permanent` | 4 暴恐犯罪 | 0.97 | 1 | `permanent` | critical + 0.95+ + 1 次前科 |
| `permanent` | 0 其他违禁 | 0.99 | 5 | `ban_1h` | low 严重度上限为 1 小时 |
| `ban_1h` | 5 广告诈骗 | 0.58 | 0 | `none` | 置信度低于 0.60 |
| `ban_1m` | 5 广告诈骗 | 0.96 | 2 | `ban_1m` | 服务端不升级，尊重较低建议 |

#### 4.4.7 审计字段

在 `chat_risk_judgements` 增加：

```sql
punishment_requested VARCHAR(32) NULL,
punishment_applied VARCHAR(32) NULL,
ban_seconds INT NULL,
policy_adjusted TINYINT(1) NOT NULL DEFAULT 0,
policy_note VARCHAR(255) NULL
```

这样可以看到：

- Agent 本来建议什么；
- 服务端最终执行什么；
- 是否被降级；
- 降级原因（置信度不足、严重度上限、无前科等）。


结构建议：

```json

    "0.60": "ban_1h",
    "0.80": "ban_1d",
    "0.90": "ban_3d",
    "0.95": "permanent"
  },
  "reasonSeverity": {
    "0": "low",
    "7": "low",
    "3": "medium",
    "6": "medium",
    "1": "high",
    "2": "high",
    "127": "high",
    "-128": "high",
    "4": "critical",
    "5": "critical"
  },
  "severityCaps": {
    "low": "ban_1h",
    "medium": "ban_1d",
    "high": "ban_3d",
```

阈值可调整，但所有调整必须保留单元测试，避免误封。

### 4.5 Agent 调用方式

- 使用 `@earendil-works/pi-coding-agent` SDK 创建内存会话。
- `tools: []`，禁止 Agent 读写文件或访问数据库，避免越权。
- 模型使用 Pi 当前配置的默认模型，或通过 `CHAT_AGENT_MODEL` 指定。
- 每次分析创建独立内存 session，避免上下文串号。
- 超时 `CHAT_AGENT_TIMEOUT_MS=20000`，超时放弃本次封禁。
- 全局并发 `CHAT_AGENT_CONCURRENCY=2`，每个账号同一时间最多一个分析任务。
- 同一账号连续发送消息时，使用 1~2 秒防抖合并，避免每条消息都调用一次模型。

## 5. 数据库变更

现有表：

- `chat_risk_logs`：原始日志。
- `chat_risk_judgements`：Agent 判断结果。

`chat_risk_judgements` 需要新增处罚审计字段：

```sql
ALTER TABLE chat_risk_judgements
  ADD COLUMN punishment_requested VARCHAR(32) NULL AFTER evidence,
  ADD COLUMN punishment_applied VARCHAR(32) NULL AFTER punishment_requested,
  ADD COLUMN ban_seconds INT NULL AFTER punishment_applied,
  ADD COLUMN policy_adjusted TINYINT(1) NOT NULL DEFAULT 0 AFTER ban_seconds,
  ADD COLUMN policy_note VARCHAR(255) NULL AFTER policy_adjusted;
```

新增表：

```sql
CREATE TABLE chat_player_bans (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  account VARCHAR(128) NOT NULL,
  log_id VARCHAR(64) NULL,
  judgement_id BIGINT UNSIGNED NULL,
  reason INT NOT NULL,
  label VARCHAR(64) NOT NULL,
  punishment VARCHAR(32) NOT NULL,
  duration_seconds INT NULL,
  start_at DATETIME(3) NOT NULL,
  end_at DATETIME(3) NULL COMMENT 'NULL 表示永久',
  status ENUM('active','expired','lifted') NOT NULL DEFAULT 'active',
  lifted_at DATETIME(3) NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_bans_account_status_end (account, status, end_at),
  KEY idx_bans_judgement (judgement_id),
  CONSTRAINT fk_bans_judgement
    FOREIGN KEY (judgement_id) REFERENCES chat_risk_judgements (id)
    ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

说明：

- `end_at IS NULL` 表示永久封禁。
- 一个账号可能存在多条历史封禁；只允许一条 active。
- 手动解封更新 `status='lifted'`，不删除历史。
- 新增迁移文件：`db/migrations/002_player_bans.sql`。
- 新增迁移文件：`db/migrations/003_judgement_policy.sql`。
- 一个账号同时只允许一条 active 封禁；创建新封禁前先检查。

技术建议：**原生 HTML + CSS + JavaScript**，由 Node 服务直接托管，不引入前端构建链。

页面布局：

```text
┌──────────────┬─────────────────────────────────────┐
│ 玩家列表      │ 当前玩家：清风   [切换玩家 ▼]        │
```

功能点：

5. 顶部封禁横幅显示原因、处罚时长、剩余时间。

7. SSE 实时更新其他标签页/玩家状态；断线时轮询兜底。

## 8. 并发与性能

1. 每个账号一个分析队列，避免同一玩家并发调用模型。
2. 连续消息防抖 1.5 秒；只分析最新窗口。
3. 全局模型并发 2，避免本地服务打满。
4. 单次分析超时 20 秒；超时降级为不封禁。
5. 窗口消息最多 50 条；超出时截断最早消息。
6. 发送消息接口不等待模型，返回 202；分析结果通过 SSE 推送。
7. 数据库连接复用现有 `getDbPool()`。
8. 服务默认绑定 `127.0.0.1:3000`，避免暴露公网。

- 仅监听 `127.0.0.1`，本地演示不开放公网。
- 数据库密码继续放在 `config/database.json`，该文件已 gitignore。
- Agent 不加载任何工具，不能访问文件、数据库或执行命令。
- 前端消息做长度限制（例如 2000 字符）和基础 XSS 转义。
- API 不返回数据库密码、完整 Agent Prompt。
- 手动解封接口仅限本地演示，不做鉴权；如后续开放公网，必须加管理员登录。

## 10. 测试计划

### 10.1 单元测试

- 窗口选择：10 分钟 / 50 条截断。
- 封禁校验：active、expired、lifted、永久。
- 处罚护栏：低置信度、非法动作、永久降级。
- Agent 输出解析：合法 JSON、Markdown 包裹、非法 JSON。
- 防抖队列：同账号连续消息只触发一次分析。

### 10.2 数据库集成测试

- 发消息 → 写入日志。
- 封禁 → 插入 ban；再次发送返回 423。
- 到期 → 自动过期并可发送。
- 提前解封 → 状态 lifted，可发送。
- 切换玩家 → 只返回对应账号消息。

### 10.3 服务测试

- 启动服务，访问前端页面。
- 用 `fetch` 模拟发送消息、封禁、解封。
- Agent 使用 mock adapter 做确定性测试；真实模型做手工 smoke test。
- 可选 Playwright 做前端 E2E。
